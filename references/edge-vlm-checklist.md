# 端侧多模态推理 / 投机解码专项审计

用于小型 VLM（尤其约 1B–4B）、边缘 GPU、异构内存、视觉 token 长上下文、KV Cache 和 speculative decoding 的科研 idea。以下是审查框架而非对任何实际系统表现的断言。

## 先定真实瓶颈，避免技术先行

询问并测量：目标设备和软件栈是什么？任务是图片描述、OCR、VQA、视频还是交互助手？数据分布、图像数量/分辨率、视觉 token 数、文本输入输出长度、batch、采样模式？

将系统时间粗拆成：图像预处理/视觉编码、语言 prefill、语言 decode、KV cache 管理、草稿生成、target 验证、调度/同步、CPU-GPU 拷贝。不要把 token/s 提升等同于 end-to-end 用户体验提升。

## 推荐指标

| 问题 | 核心可观察指标 | 常见混杂变量 |
|---|---|---|
| 交互延迟 | TTFT、端到端 latency、p50/p95 | 图片编码、prefill 和 warmup 被漏算 |
| Decode 性能 | TPOT、decode tok/s、总输出 token | 不同输出长度、采样和 batch |
| 内存/能耗 | 峰值内存、KV 占用、功耗/每 token 能量（可测时） | 统一内存与分立显存统计口径 |
| 投机收益 | 每轮 accepted length、draft 时延、target 验证时延、额外拷贝 | draft 成本超过验证收益 |
| 任务质量 | 指定数据集准确率、CIDEr 等与误差样例 | 不同视觉编码、提示词或量化 |
| 可靠性 | 运行稳定性、失败率、不同任务和分辨率 | 单一 prompt 或样本过少 |

保持 target model、分词器、采样设置、prompt、图像处理、硬件功耗模式及软件版本一致；在充足 warmup 后做重复测量并报告变异。若目标是精确保持目标模型采样分布，必须核验接受/拒绝及残差修正的条件，**不能仅比较速度和看似相同输出**。

## 投机解码必须追问的机制问题

1. 无训练草稿来源是什么？小模型、n-gram、logit 映射、启发式 token proposal、轻量 head 还是基于隐藏状态？每种方案能否实际访问它所需的 state/logits/KV？
2. 如果声称“免训”，究竟是完全不更新参数，还是使用离线统计、缓存、校准集或蒸馏？训练成本与线上开销分别计算。
3. 草稿 token 是否依赖视觉信息？视觉上下文改变 draft/target 的条件概率分布吗？是否因为文本先验强，在开放式描述看似有效但在 OCR/细节问答失败？
4. target 验证是否能并行计算？验证成本是否随草稿长度、图像 token 数和硬件后端变化？是否发生额外 KV 合并/回滚/同步？
5. 观察到的 speedup 是相对“同一个 target 的优化 baseline”吗？是否把基础模型推理速度差异当作解码策略差异？
6. 采样分布保持（lossless/exact）还是接受近似结果？若近似，则质量-速度 trade-off 与相应评价不可省略。

## 最小数量级核算

定义 `T_base`：target 单独生成同等输出的时间；`T_draft`：生成候选的耗时；`T_verify`：target 验证的耗时；`T_misc`：调度、同步、KV、回退等开销。对一次固定测量窗口可写：

`measured_speedup = T_base / (T_draft + T_verify + T_misc)`

若输出 token 数不等，必须先对齐工作量或使用端到端同任务比较，不可直接代入。候选平均接受长度高也不必然加速：目标验证调用次数降低所节省的时间必须超过草稿和协调开销。任何理论速度估计都只能视为实验前的成本模型。

## 端侧专项最小实验矩阵

至少比较：(A) target-only 优化 baseline，(B) draft+verify 方案，(C) 去掉新增机制的消融；再按任务类别（视觉依赖强/弱）、图像 token 数、输入/输出长度分层。资源有限时先在一小批固定样本上确定瓶颈，再扩大到严谨评测。

对 unified memory 与 discrete VRAM 之类架构比较，应控制 backend、精度、batch、功耗和内存带宽差异，不能因为观测不同就直接声称由“统一内存”单一因素导致。若无法控制，写成系统层关联发现而非因果结论。

## 非训练贡献的判定

没有训练仍可能产出：推测解码接受率随视觉条件变化的机制研究、架构依赖成本模型、可移植的调度/缓存算法、严谨的任务失效边界、可验证的系统设计。仅将现有 draft 接到某个 VLM 并获得加速，通常还需要额外机制分析、跨设置验证或新技术解决瓶颈，才能支撑较强研究贡献。

## 快速查验提纲

- **问题**：哪个真实 workload 上 target-only 的哪一部分是瓶颈？
- **假设**：什么机制使 draft 的预测在这里更有利？
- **负例**：OCR/高视觉依赖、长视觉上下文、短输出、低接受率会不会完全抵消收益？
- **对照**：与强 baseline 相比是否净收益？
- **代价**：额外模型、参数、缓存、内存、功耗、实现复杂度、兼容性？
- **贡献**：新知识究竟是算法、系统权衡还是失败规律？
